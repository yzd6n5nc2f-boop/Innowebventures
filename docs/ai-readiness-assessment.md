# AI readiness assessment

Public page: `/ai-readiness-assessment`. Uses the existing `/api/workflow-assessment` endpoint with `assessmentType: readiness`. Existing workflow submissions remain supported with their original result format. No new credentials or model subscription are needed. Recipient cooldowns are scoped to assessment type so a visitor can complete both tools; shared network and daily limits still apply. On confirmed delivery failure the recipient cooldown is released; the single-use token and network/daily limits remain. Refresh the email form before retrying. Server-side scoring, rate limits, signed tokens and delivery adapters are shared with the workflow assessment.

The 12 questions and option scores are in `api/lib/readinessQuestions.json`, imported by both the website and server. Each answer contributes 0–3 points, maximum 36. Bands are 0–14 foundations, 15–26 pilot, 27–36 controlled rollout. Documented local, private-cloud and cloud requirements score equally. This is a self-assessment, not certification. Critical human-review and privacy gaps are flagged even when the overall total is high. Priorities come from the three lowest proportional dimension scores.

Name, email and assessment-processing consent are required before the API returns the full result. The participant receives the full result and all answers through the existing configured transactional provider (Brevo in production); the configured CONTACT_TO_EMAIL inbox receives a separate result notification including optional personal-follow-up choice. No marketing list is created or updated. Production delivery acceptance is not proof of inbox arrival. Monitor provider logs and the notification inbox.

The review-call button links to `/contact?intent=ai-readiness-review`, where the visitor requests a call and the team agrees a time. No calendar booking is claimed. All four service-detail pages and the services overview include the assessment CTA. The navigation points to this assessment, with a direct link onward to the workflow assessment. Sitemap, initial HTML, metadata and llms.txt are generated by the normal build.

Run `npm run test:assessment` and the existing site checks. Tests cover threshold boundaries, completeness, forged result rejection, privacy-neutral hosting scores, high-score safeguards, consent and participant/team delivery. Browser QA should exercise all three question steps, required selection, backwards navigation, consent gate and result screen.
